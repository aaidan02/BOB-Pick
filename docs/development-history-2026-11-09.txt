밥픽(BOB Pick) 개발 과정 메모
정리 기준: 2026년 11월 9일, 한국 시간
기준 코드: b6ae4217583af2465a8991057bfb6a2e3cae0ea7

이 파일은 지금까지의 대화와 현재 코드를 토대로 정리한 진행 기록이다.
초기 단계의 정확한 작업 날짜는 확인할 수 없어 순서로 정리했다.
대화 원문을 그대로 옮긴 파일은 아니다.

==================================================
1. 처음 만들려던 것
==================================================

음식을 고르기 어려운 사용자가 버튼을 누르면 메뉴를 추천받고,
그 메뉴를 판매하는 음식점 위치를 지도에서 확인하는 프로그램을 구상했다.

처음에는 naver-map-test.html, RandomFoodPicker.java와 기존 class 파일,
둔산동 음식점 CSV를 결합하는 방향으로 시작했다.
실행 환경은 Windows와 VS Code였다.
수정한 Java 소스는 다시 컴파일하고 실행하도록 정리했다.

==================================================
2. 실행 문제와 한글 처리 정리
==================================================

ZIP 저장 문제와 Java 실행 문제를 확인하고 실행 방법을 안내했다.
JDK 설치, 컴파일, 실행 경로와 classpath를 맞추는 과정이 있었다.
FoodPickerWeb 클래스를 찾지 못하는 문제는 출력 파일 위치와
실행 시 검색하는 경로가 맞는지 확인하는 방식으로 정리했다.

PowerShell에서 bobPickJdk가 명령으로 인식된 오류는 변수 앞의
$가 빠진 명령과 관련이 있었다. $bobPickJdk처럼 변수 문법을 사용한다.
서버 시작 메시지가 출력되었다면 그 메시지와 앞선 명령 오류를 구분했다.

한글 깨짐은 한 가지 인코딩 문제로 묶지 않고 구분했다.
- Java 소스와 웹: UTF-8
- 기존 음식점 CSV: CP949/MS949
- 터미널: 출력 인코딩과 Java 실행 설정 확인

현재 클라우드 웹 버전은 Java 서버 없이 Node.js 개발 도구로 실행한다.
기존 Java 방식은 이전 버전 문서에 보존했다.

==================================================
3. 폐업 확정 자료만 제외
==================================================

사용자는 폐업이 확정된 음식점만 제거하도록 요청했다.
미확정과 미확인 데이터는 삭제하지 않는 기준을 확정했다.
CSV 처리와 프로그램 로딩에서 이 구분을 유지했다.

현재 보존된 CSV는 음식점 808행이며,
클라우드 이전도 이 808곳을 초기 음식점 자료로 사용했다.

==================================================
4. 가격·음식 종류·음식 형태 조건 도입
==================================================

가격, 음식 종류, 음식 형태로 검색할 수 있도록 확장했다.
조건을 고르지 않으면 전체에서 랜덤으로 고르는 기본값을 유지했다.

초기에는 업종 정보와 메뉴 설명을 어떻게 구분할지 논의했다.
이후 CSV에 음식 종류와 음식 형태 컬럼을 정리해 사용하도록 방향을 잡았다.
최종적으로 음식 종류는 CSV 등록값을 유지하고,
음식 형태는 가게의 다양한 메뉴와 연결해 검색하는 기준을 사용한다.

검색 대상을 대표 메뉴에만 한정하지 않고 메뉴한글명의 전체 메뉴로 넓혔다.
한 가게 안에서도 조건에 맞는 실제 메뉴를 찾아 표시하도록 했다.

예시:
미향일식, 음식점 ID 15779의 대구탕이 국·탕·찌개 형태에 걸려야 한다.
형태 조건은 A 메뉴에서, 가격 조건은 B 메뉴에서 만족하는 식으로
서로 다른 메뉴를 섞어 조건을 충족시키지 않는다.

가격 입력 화살표는 1원 대신 1,000원 단위로 움직이게 했다.

==================================================
5. 영업시간을 실제 조회 조건으로 정리
==================================================

막연히 아침·점심·저녁 등으로 분류하는 방식은 목적에 맞지 않았다.
검색하려는 날짜와 시각에 영업하는지를 판단하는 형태로 바꿨다.

기본 날짜·시각은 Asia/Seoul의 현재 시간이다.
사용자가 직접 시간을 넣으면 그 방문 일시로 검색한다.

요일별 영업 구간, 휴게시간, 라스트오더, 자정이 지난 영업,
정기휴무와 공휴일 예외를 처리하도록 정리했다.
모르는 시간과 휴무를 같은 상태로 보지 않도록 구분했다.

CSV 이름을 관내 음식점 텍스트 데이터셋_둔산동_재검토_2.csv로 바꾸었고,
현재 코드와 데이터 이전에서도 이 이름을 사용한다.

==================================================
6. 화면 디자인과 추천 유지 문제 수정
==================================================

처음에는 제공한 밥픽 개발계획서 PPT의 화면 시안을 참고했다.
주황색, 크림색, 둥근 카드와 밥그릇 캐릭터를 적용했다.

사용자가 필요 없다고 한 자료 기준·실시간 여부·영업 상태 등의
설명 문구는 추천 화면에서 제거했다.

추천 후 오늘의 추천 메뉴가 사라지는 문제를 확인했다.
현재 시각과 후보 수를 자동 갱신하는 동작이 이미 뽑은 결과를
지우지 않도록 추천 카드·고정·지도 상태와 분리했다.
사용자가 검색 조건을 직접 바꿀 때는 새 조건으로 다시 검색한다.

==================================================
7. 네이버 지도와 출발지 처리
==================================================

추천 가게의 위치 표시와 네이버 길찾기 연결을 구현했다.
길찾기는 추천 음식점을 도착지로 전달한다.

처음에는 사용자 위치를 출발지에 넣는 방향도 논의했지만,
사용자는 GPS가 없으면 출발지를 설정하지 않도록 요청했다.
브라우저 API는 GPS와 Wi-Fi 등 측정 출처를 확정해 주지 않으므로,
임의의 위치를 추정해 출발지에 넣지 않는 방식으로 정리했다.
위치 확인은 별도 진단 화면으로 분리했다.

나중에 길찾기 목적지 연결을 다시 확인하면서 좌표를 검증하고
좌표로 전달하는 목적지를 SIMPLE_POI 형식으로 고쳤다.
좌표가 없으면 음식점 이름·주소로 검색하도록 했다.
늦게 로딩되는 지도 SDK도 초기화할 수 있도록 보완했다.

사이트 내부 지도 인증을 위한 네이버 클라우드 도메인 등록은
사용자가 당장 진행할 수 없다고 하여 보류했다.

==================================================
8. 여러 음식점 추천과 가게 고정
==================================================

기본 설정으로 버튼을 누르면 기존처럼 가게 한 곳만 보여준다.
조건을 지정하면 서로 다른 가게를 최대 세 곳까지 보여준다.
자동으로 들어간 현재 시간만으로 세 곳 추천이 되지는 않는다.

마음에 들어요를 체크한 카드는 가게·메뉴·가격을 현재 자리에 고정한다.
새로고침을 누르면 고정하지 않은 카드만 다시 추첨한다.
고정한 가게와 중복되지 않도록 하고, 후보가 충분하면 새 가게를 우선한다.
후보가 한두 곳이면 중복으로 세 칸을 채우지 않는다.

이 화면 고정은 현재 추천을 유지하는 기능이다.
이후 추가한 계정별 메뉴 찜 저장과는 별도 기능으로 구분했다.

==================================================
9. AI 채팅 추천과 수동 검색 분리
==================================================

사용자의 자연어 채팅을 읽고 실제 음식점·메뉴 중에서 골라주는
Gemini API 기반 추천을 추가했다.

AI가 응답하지 않거나 약 70~80초 뒤 오류가 발생하는 문제를 점검했다.
조건 해석과 후보 선택이 이어지는 요청 구조, 대기 시간과 오류 처리를 정리했다.
수동 검색 버튼이 AI 추천처럼 보이거나 AI를 호출하는 혼동도 수정했다.

현재는 다음처럼 구분한다.
- 수동 검색: 사용자가 입력한 필터와 DB의 후보로 랜덤 추천
- AI 채팅: 채팅 내용에서 조건을 해석하고 실제 DB 후보 중 선택
- AI가 고른 ID와 메뉴는 서버가 후보 목록과 대조
- 늦게 도착한 응답은 최근 검색 결과를 덮어쓰지 않음

검색 결과가 생기면 결과 화면으로 자동 스크롤한다.
AI 추천이 완료되면 우측 하단 초록색 성공 알림을 띄우고 3초 뒤 없앤다.

이전 Java 버전은 실행할 때마다 API 키를 터미널에서 입력받았다.
붙여넣기 처리와 숨김 입력 여부를 확인하는 안내도 보완했다.
현재 배포 버전은 Supabase Secrets에 키를 설정해 서버에서 사용한다.
이전 터미널 입력 방식과 현재 서비스 설정을 혼동하지 않도록 구분했다.

==================================================
10. 태평소국밥 가격 예외 처리
==================================================

가격에 한글 설명이 섞여 숫자를 못 읽는 경우를 보완했다.
일반 고정 금액은 숫자를 해석하지만 변동가격 문구가 있으면
숫자가 붙어 있어도 변동가격으로 표시하기로 확정했다.

예시:
[7000, 변동가격(업주문의)26000, 변동가격(업주문의)8500, 7000, 17000]

이 자료는 메뉴가 7개이고 가격은 5개여서,
앞에서부터 순서대로 연결하고 남은 메뉴는 가격 표시 없음으로 정했다.
없는 가격을 추정해서 채우지 않는다.
변동가격과 가격 미확인 메뉴는 숫자 가격 조건에서 제외한다.

==================================================
11. 실제 서비스 구조로 전환
==================================================

회원, 찜, 커뮤니티, 관리자 기능을 추가하고 외부에서 접속할 수 있게
Supabase와 Vercel을 사용하는 구조로 전환했다.

최종 선택한 구성:
- Vercel: 웹 화면 배포
- Supabase Auth: 회원·로그인
- Supabase PostgreSQL/RPC: 데이터와 추천·관리자 처리
- Supabase Edge Functions: Gemini API 호출과 후보 검증

현재 웹 운영에는 별도 Java 서버가 필요하지 않다.
기존 Java 소스와 설명은 남겨 비교·데이터 이전·기존 버전 실행에 사용한다.

회원 공통키는 Supabase Auth의 auth.users.id를 사용한다.
프로필, 메뉴 찜, 게시글, 신청, 검토자와 변경 이력을 이 키로 연결했다.
음식점과 메뉴는 회원과 독립적으로 두었다.

Supabase BOB-Pick 프로젝트에 마이그레이션 4개와 초기 자료를 적용했다.
음식점 808곳, 메뉴 5,086개를 옮겼고 원래 CSV 컬럼도 보존했다.
폐업 미확정·미확인 자료를 임의로 삭제하지 않았다.

==================================================
12. 회원·찜·커뮤니티·관리자 구현과 배포
==================================================

회원가입, 이메일 확인, 로그인·로그아웃, 비밀번호 재설정,
닉네임 변경과 계정별 메뉴 찜 저장·해제·목록을 구현했다.

커뮤니티는 글 작성·검색·조회·본인 글 수정·삭제를 구현했다.
문의·신청은 정보 수정, 음식점 등록, 홍보 신청과 본인 내역 조회를 구현했다.
관리자는 승인·반려하고 처리 사유와 변경 전후 이력을 남긴다.
정보 반영과 이력 기록은 하나의 트랜잭션으로 처리한다.

화면에서 버튼만 숨기는 데 그치지 않고 DB의 RLS로 권한을 제한했다.
관리자 계정도 별도 권한 테이블로 연결했다.

GitHub 저장소와 Vercel 연결, 공개 환경변수와 Auth URL을 설정했다.
Gemini 키는 사용자가 Supabase Secrets에서 직접 등록했다.

운영 주소: https://bob-pick.vercel.app
저장소: https://github.com/aaidan02/BOB-Pick
작업 브랜치: feat/supabase-vercel-service

13. 문의 신청에서 음식점 검색 추가
==================================================

긴 음식점 선택 목록만 사용하는 대신 이름·주소·ID로 검색할 수 있게 했다.

==================================================
14. 관리자·문의 내역 오류와 게시글 권한 수정
==================================================

발생한 오류:
object is not iterable (cannot read property Symbol(Symbol.iterator))

원인:
request_reviews.request_id가 UNIQUE 외래키인 일대일 관계여서
PostgREST가 처리 결과를 배열이 아닌 객체 또는 null로 반환했다.
화면에서는 이를 배열처럼 반복해 읽어 승인·반려 내역 표시가 실패했다.

수정:
- 일대일 객체/null 응답을 정상적으로 처리
- 관리자 목록과 내 신청 내역에서 가게 이름·상태·처리 사유 표시
- 내부 JavaScript·DB 오류는 한국어 안내로 변환
- 실제 관계 형태가 테스트에서도 재현되도록 대역 서버 수정
- 목록 새로고침으로 다시 시도할 수 있게 구성

커뮤니티는 제목만 누르는 대신 게시글 줄 전체를 눌러 열리게 했다.
키보드로 펼치고 접는 동작도 확인했다.

관리자는 다른 회원 글을 삭제할 수 있도록 버튼과 요청 조건을 고쳤다.
관리자 삭제 요청에는 작성자를 본인으로 제한하는 필터를 붙이지 않는다.
대신 DB의 작성자 또는 관리자 권한 검사는 그대로 유지한다.
실제로 삭제된 행도 확인하며 일반 회원의 다른 사람 글 삭제는 차단한다.
다른 사람 글을 수정할 수 있는 권한은 추가하지 않았다.

15. 전체 UI를 당근처럼 친숙하게 정리
==================================================

사용자가 불친절하다고 한 전체 화면을 다시 정리했다.
밥픽 이름과 캐릭터를 유지하면서 주황색·흰색 중심으로 변경했다.

- 모바일에서 항상 접근할 수 있는 하단 이동 메뉴
- 홈에서 수동 조건 검색을 먼저 표시하고 AI 채팅을 별도로 배치
- 동네 이야기 목록과 명확한 글쓰기 버튼
- 로그인·회원가입, 내 찜, 문의·신청 화면 구성 정리
- 대기·승인·반려 상태 배지와 읽기 쉬운 처리 사유
- 추가 지도 좌표처럼 선택적인 항목은 접어서 표시
- 결과가 한 곳이면 불필요한 빈 카드 칸을 만들지 않도록 배치
- 추천 결과가 상단 고정 메뉴에 가리지 않도록 스크롤 위치 조정

16. 확인한 테스트와 운영 반영
==================================================

최근 코드 기준으로 다음 검증을 통과했다.
- 웹 프로덕션 빌드와 타입 검사
- DB·권한·추천·길찾기 테스트 15개
- 브라우저 시나리오 10개
- Java와 SQL 영업시간 판정 비교 24,420개 조건
- GitHub Actions의 push 및 PR 검사

주요 검증 사례:
미향일식 대구탕, 태평소국밥 가격 예외, 단일/세 곳 추천,
카드 고정, 메뉴 찜 유지, 커뮤니티 작성·수정·삭제,
관리자의 다른 회원 글 삭제, 일반 회원의 권한 차단,
승인·반려 후 내역 표시, 한국어 오류와 재시도, 모바일 화면.

최종 기능 수정 코드는 b6ae4217583af2465a8991057bfb6a2e3cae0ea7이다.
Vercel 프로덕션 READY 상태와 운영 주소의 HTTP 200,
새 빌드 파일이 실제 HTML에 반영된 것을 확인했다.

자동 브라우저 테스트는 로컬 Auth/PostgREST 대역과 PostgreSQL을 사용했다.
실제 Gemini 응답, 이메일 전달, 네이버 지도 인증과 휴대폰 위치 수신은
각 외부 서비스와 실제 기기에서 확인해야 하는 범위로 구분한다.

17. 현재 남아 있는 확인 사항
==================================================

1) 네이버 클라우드 Maps 운영 도메인 등록과 실제 지도 표시 확인
2) 실제 계정의 확인 메일·재설정 메일·메뉴 찜 재접속 확인

4) 실제 휴대폰에서 HTTPS 접속·화면·길찾기·위치 진단 확인
